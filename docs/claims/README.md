# 작업 클레임 (병렬 워커용 lock)

여러 워커가 여러 계정에서 동시에 돌기 때문에 **작업 단위로 선점**한다. (aaawunity `docs/claims/README.md` 규약 그대로)

- 파일명: `<작업ID>.lock` (예: `T2.lock`) — 작업ID = `docs/PROGRESS.md` 표의 ID.
- **한 번호는 한 작업만 가리킨다.** 신규 작업 번호는 눈으로 찾지 말고 `python3 tools/task_state.py --new-id` 로 뽑는다 — 그 자는 **표와 커밋 이력 중 큰 쪽** +1 이다(표는 행이 지워지면 줄어들지만 커밋 제목은 append-only 다).
  - **작업을 접을 때 행을 지우지 않는다 — `✂` 로 남겨 번호를 태운다.** 지우면 그 번호가 되살아난다.
  - 같은 순간 둘이 같은 번호를 뽑는 갈래는 못 막는다 — 그것을 가르는 것은 아래 **push 순서**다(늦게 민 쪽이 제 번호를 옮긴다).
- 내용 1줄: `<UTC ISO8601> <SID>` 예) `2026-09-12T01:30:11Z sess-0130-8412`
- 선점 절차: **① `docs/PROGRESS.md` 표에서 그 작업의 «상태» 칸을 읽는다 — ⬜ 가 아니면 잡지 않는다**(✅ = 끝난 것 · 🔄 = 임자가 하고 있거나 방금 반납한 것) → ② `python3 tools/task_state.py <ID>` 가 0 → ③ lock 파일 생성 → 커밋(`[skip ci]`) → **push. push 가 먼저 성공한 쪽이 이긴다.**
  push 충돌 시 `git fetch && git rebase origin/main` 후 자기 lock 이 살아있는지 확인 — 사라졌거나 남의 lock 이 있으면 포기하고 다음 작업으로.
- **90분 지난 lock 은 죽은 것으로 보고 뺏는다**(뺏을 때 기존 파일을 자기 SID 로 덮어 커밋·push). 장기 세션은 90분 전에 타임스탬프를 갱신해 push 한다 — 그것이 «살아 있다» 는 유일한 신호다.
- 작업이 끝나거나 중단되면 성공·실패 무관 **반드시 삭제**한다. 단 **«CI 가 그 커밋을 한 번은 돈 뒤»** 반납한다(ROUTINE §1).

## ⚠ «직전 슬롯 세션의 lock» 도 남의 lock 이다

**같은 워커 문자(A~P·Q)라도 SID 가 다르면 다른 세션이고, 그 lock 은 90분 규약을 그대로 적용한다.** 다른 계정의 lock 도 남의 lock 이다.
«앞 세션이 등재만 하고 끝났겠지» 라는 추정으로 인계하지 말 것 — 앞 세션은 자주 아직 살아 있다.
- ⓐ `date -u` 와 lock 타임스탬프로 **90분이 실제로 지났는지** 계산한다.
- ⓑ 90분 전이면 그 작업은 **건드리지 않고** 다른 작업을 잡거나, 열린 작업이 그것뿐이면 **아무것도 안 하고 물러난다**.

## 이 레포만의 추가 규약

- 한 작업이 만지는 파일 범위는 PROGRESS 표의 «범위» 열에 적힌 폴더·파일이다. **두 작업이 같은 파일을 만져야 하면 뒤 번호가 기다린다.** 범위에 없는 파일을 열게 되면 표의 «범위» 칸을 먼저 고쳐 push 한다(`check_claim_scope.py` 가 그것을 본다).
- `Assets/StreamingAssets/data/*.json` 은 어느 작업도 손으로 고치지 않는다 — `node tools/export_data.js`(T2)로만 갱신한다.
- 커밋 제목은 `T<번호> …` 로 시작한다(`check_claim_scope` 가 그 번호로 «그 작업의 커밋이 만진 파일» 을 센다).
